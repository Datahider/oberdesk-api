# API v1

`v1` импортирован из фактического production-состояния `api.oberdesk.ru`.

## Размещение

- Production: `/home/oberdesk-api/htdocs/api.oberdesk.ru/v1`.
- Публичный URL: `https://api.oberdesk.ru/v1`.
- Конфигурация: `v1/etc/config.php`, вне Git.
- Зависимости: `v1/vendor`, вне Git.

## Существующие маршруты

- `GET /v1/me`;
- `GET /v1/groups`;
- `GET /v1/group/{group_id}`;
- `GET /v1/group/{group_id}/threads`;
- `GET /v1/thread/{thread_id}`;
- `GET /v1/thread/{thread_id}/messages`.
- `GET /v1/pacer/time-entries?subject={id}&project_group={group}&from={ISO-8601}&to={ISO-8601}`.

На момент импорта `/me` и `/groups` используют серверную конфигурацию и БД. Остальные маршруты частично возвращают тестовые данные из `StubData`.

## Pacer time entries

Метод возвращает интервалы учёта времени для пейсера:

- `subject` — обязательный положительный Telegram ID авторизованного пользователя;
- таймер определяется сервером по точному совпадению `timers.subject`; отсутствие таймера или несколько таймеров для одного пользователя считается ошибкой данных;
- `project_group` — обязательное точное значение `chat_groups.chat_group`;
- включаются только события выбранного таймера, у которых `timer_events.project` входит в выбранную группу проектов;
- `from` включается, `to` не включается;
- незавершённое событие заканчивается текущим моментом;
- ответ содержит `id`, `task_id`, `task_type`, `started_at`, `ended_at`, `duration_seconds` и `is_running`;
- значения MySQL `DATETIME` интерпретируются как `Europe/Moscow` и возвращаются с корректным смещением `+03:00`;
- `task_type` берётся из `topics.type`, отсутствие связанной задачи является ошибкой данных;
- метод только читает БД.

## Деплой

1. Изменения отправляются в `master`.
2. Создаётся новый GitHub tag/release.
3. От пользователя `oberdesk-api` запускается `/home/oberdesk-api/htdocs/update-api.sh VERSION`.
